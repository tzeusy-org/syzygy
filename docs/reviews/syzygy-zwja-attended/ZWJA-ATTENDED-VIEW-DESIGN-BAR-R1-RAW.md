## F1 — Live reattachment and continuation of a stopped run remain ambiguous

[Observed] `design.md:131–141` treats detach and reattach as inherited multiplexer capabilities. Candidate REQ-043 requires the detached interval and says panes survive. It leaves the run/attempt binding, start/open/end evidence, stale view handling and repeat semantics implicit. Its printed-action prose names attach and stop together, while its stop scenario names resume, with no rule for choosing what the operator sees when the old view exists and the run is stopped or cleanup is still unverified. An operator reattaching after a wait can mistake a present pane for current progress or take the input that starts a new attempt. That fails the design bar's recovery, repetition and first-glance questions. The supplied detach, reattach, missing receipt, pending cleanup, stopped, refused resume and repeated-attach counterexamples discriminate those states.

[Inferred] A minimal candidate design amendment can require a same-run, same-attempt detach receipt with explicit open interval, observed reattach endpoint and original deadline. The live view offers attach and an observed state or reasoned Unknown. A verified stopped run offers resume under the existing pin, deadline and authorization checks. During stop, the display identifies pending cleanup and never claims success based on a pane disappearing. A refused resume preserves the previous state and records the reason. Attaching twice reads the same run and starts no work. Make these obligations falsifiable in the candidate by mutating interval identity, omitting an endpoint, replaying a stale view, swapping actions, repeating the command and separating stop request from verified cleanup. The existing adopted bounded state reader and cleanup checks remain the governing behavior.

## F2 — The wait cue needs a safe keyboard path and an identifiable reason

[Observed] Candidate REQ-043 and `design.md:135–136` identify an unanswered question's pane, but the design does not specify how an operator without a mouse or color finds and focuses it, how a narrow plain-text terminal preserves stage and action, or how an unavailable wait observation is distinguished from a user-action request. Historical REQ-043 additionally makes each helper pane interactive. Effective REQ-048 binds each URL role to fixed admitted inputs and tools. This review can credit the view-only state, owner question location and recovery copy without crediting a new way to send helper inputs or widen role permissions. The failure modes are a busy-only line, dependence on a highlighted/clickable pane and a continuing claim with no current view receipt.

[Inferred] Add one textual question-versus-system-wait rule with source/attempt and observation time, explicit non-color keyboard focus and help cues, and a reasoned Unknown when the same-run proof is missing. Keep the permitted author question path subject to its existing authorization. Other role panes can expose only the admitted scoped status in this view design. An operator typing arbitrary helper input is outside the review's proposed surface. Measure real acknowledgement, keyboard focus and assistive-terminal announcement independently when an authorized runnable surface exists. The attached design examples verify that the specified cues can be distinguished, without claiming timing or accessibility of a real tool.
