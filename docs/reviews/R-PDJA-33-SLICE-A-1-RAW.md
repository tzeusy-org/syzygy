## Findings

**Finding 1 — the read oracle is blind to the commonest read API, so reads outside the closed list can regress unseen** (revise)
[Observed] The unit and integration read oracles (`logged` in `launch-clone.test.ts`, `opened` in `launch.test.ts`) log only `node:fs` `openSync` through `patchFs`. R1 (opening `objects/info/alternates`, which read (4) forbids: "whether `objects/info/alternates` exists") and R3 (reading every loose reference's value, the exact over-read item 1b removes) both survived both tiers when written as `fs.readFileSync(path, 'utf8')`. The same reads without an encoding (R4, R5) were killed. [Inferred] On node v24 the utf8 form of `readFileSync` reads through a native fast path that never calls the JavaScript `fs.openSync`, so the layer sees nothing. The code at db109c54 does not use that form, so no unlisted read is present today; the defect is in the evidence that the list stays closed. 046's oracle requires a read-logging layer "outside the code under test", and a layer that only works when the code picks one API is not independent of the code. Repair: an API-independent oracle, e.g. fixtures whose non-admitted files (unlisted loose refs, `objects/info/alternates`, `.git/reftable` contents) are mode 000 so any open of them fails whatever API makes it; or also patch `readFileSync`, `readFile`, `promises.open`/`readFile` and `createReadStream` and assert none touches the clone's `.git`. Then add R1 and R3 to the mutation record and show them killed.

**Finding 2 — every remote's HEAD value is read even when `origin` records the default** (revise)
[Observed] Stage 2 admits every `refs/remotes/<remote>/HEAD` in `names`, unconditionally (`launch-clone.ts` admitAll after HEAD). The FULL fixture pins this: `refs/remotes/up/HEAD` is opened although `origin` records a default. [Inferred] Read (2) admits "the values … of the references the trunk rule above names". The trunk rule takes `origin`'s default "when it records one", and only otherwise asks which remotes record one. While `origin/HEAD` is symbolic, no other remote's HEAD takes part in the rule, so the implementation comment's claim that the rule "must read each to tell which remotes record a default" holds only when `origin` records none. Repair: admit `refs/remotes/origin/HEAD` first, and the other remotes' HEADs only when it is absent or not symbolic. Or, if the broader reading is intended, have the owner rule it (CC-REV-2). Either way, re-pin the FULL fixture's expected opens.

**Finding 3 — the `.git/reftable` existence probe is a read no list item names** (note)
[Observed] `lstatSync(path.join(gitDir, 'reftable'))` runs before HEAD. [Inferred] The list treats existence as a read: it lists "whether `objects/info/alternates` exists" explicitly. No item names `.git/reftable`. The refusal duty ("a clone that stores its references otherwise … SHALL be refused") names no detection read. The HEAD placeholder, a listed value, already catches every Git-written reftable repository (probe: HEAD is `ref: refs/heads/.invalid`), so the probe adds defence only against a HEAD rewritten within the agents' write reach. Options: drop the probe; keep it and disclose it as the detection the refusal implies; or carry the question to the owner with the slice-B statements. Not blocking: it reads no value, object or file content.

**Finding 4 — `--revision HEAD` is refused although HEAD is a reference the clone holds** (note)
[Observed] `revisionRefCandidates` starts at `refs/<name>` and omits Git's first short-name rule (the name itself under the Git directory), so `--revision HEAD` yields `resolves to no object identifier` (probe). HEAD's value is already admitted. [Inferred] Fail-closed, and pre-existing (the candidate list is unchanged from ad3346aa). Still, 047 admits "a reference the clone holds", and the refusal text is untrue for HEAD. Either admit `HEAD` as a candidate (its value is listed) or say in the refusal that HEAD is not taken.

**Finding 5 — M10 is not equivalent; the record should say "unkillable without staging the race"** (note)
[Inferred] Without O_NOFOLLOW, a link swapped in between `lstatSync` and `openSync` is followed, and the `fstatSync` check then sees the target's regular file and reads it. The two programs therefore differ under a race; no test stages one. The record's note ("[Inferred] equivalent without a race") is qualified correctly, but the mutant's own text also adds `realpathSync`, so it tests more than dropping the flag. Suggest the record call it surviving-unstaged, not equivalent, and, if cheap, kill it by patching `lstatSync` (through `patchFs`, extending `Patchable`) to report a regular file for a path that is a symbolic link.

**Finding 6 — deferral of the alternates refusal and the copy step is safe for slice A only while window 2 stays disclosed** (note)

The object reader never follows alternates (`git-object-reader.ts` 410-412, 472, 554), so an object only an alternate supplies fails closed rather than being read from elsewhere.
