## Findings

1. **Important — [Observed] — A marker is read inside a string: a template literal nested in a template substitution is mis-split, and its text is read as a comment.** `packages/polaris-dossier/src/test-names-lexer.ts:154-155` (`closeOf(text, i + 1, c, ...)` closes a template at the next unescaped backtick and ignores `${ ... }` nesting). Spec `openspec/changes/dossier-rough-edges/proposed/polaris-generation/spec.md:232` says the lexer "finds ... every string literal of the language" and "No marker is read in a string". The bead's acceptance criterion and the README say "never in a string". Evidence from the probe, in `javascript`:
   - ``const a = `${b ? `see https://github.com/o/r/issues/1 // TODO` : ""}`;`` gives `[["todo","TODO",1,...]]`. The `//` inside the inner template string is taken as a comment.
   - ``const a = `${b ? `/* HACK */` : ""}`;`` gives `[["hack","HACK",1,...]]`.

   This can happen in real code: nested templates are common in this repository's own renderers. The same defect lets a test name be read from a string under v2.42, which is pre-existing, but this change states the guarantee anew and builds an Observed row on it. Suggested repair: make the template scan track `${`/`}` depth and recurse into nested templates and strings inside substitutions. If that is too much, return `unparsed`/`unterminated` (fail closed, Unknown) when a backtick appears inside an open substitution. Add both probe lines as fixtures for markers and for test names.

2. **Medium — [Observed] — design.md gives a wrong cause for the 10 `unparsed` files.** `openspec/changes/dossier-rough-edges/design.md:21` says the 10 `unparsed` files are cases "where a template literal nests another inside a substitution and the lexer stops rather than guess". I re-derived the 10 paths on `d652b7dcc` with the commit's own derivation: `apps/three-surface-poc/src/{capture-test-artifact,page-shell,polaris-markdown,polaris,reobserve-action,trajectory}.ts` and `apps/three-surface-poc/src/polaris-generation/{diagram-layout,dossier-render-local,dossier-site,dossier-test-names}.ts`. However, the lexer does not detect nesting. ``const a = `x ${f(`y`)} z`; // TODO`` parses `ok: true`, and finding 1 shows nesting misread silently. The fault arises only when the mis-split leaves an unbalanced quote, for example an apostrophe in the inner template text. So the lexer does not "stop rather than guess": it guesses, and fails only by accident. Suggested repair: restate the cause as [Inferred], or measure it per file. After fixing finding 1, re-derive the figure.
