## Findings

### F1 — blocking — every operator-agent page gains a stylesheet the spec does not state, against its own "only changes" sentence and Falsifier

Location: subject line 84 (fragment-identity paragraph), last sentence: "These identities, the two pages below and the links to them are the only changes this version makes to an operator-agent page." Preamble, line 3: "Every operator-agent page changes by the fragment identities and navigation links this version states, and by nothing else." Falsifier, the clause added for 2.6: "an operator-agent page changes a byte other than by the stated identities and links". Scenario "Schema-v4 draft unchanged" (line 299), whose 2.6 exception lists "the fragment identities, the two finding pages, the links to them in each page's navigation and on the contents page, their entries in `dossier.json` and the size report, and the `taskRoutes` and `nameIndex` members of `machine.json`", and no style rule.

[Observed] `dossier-site.ts`, function `page`, line 206 after the change: `${DRAFT_PREVIEW_CSS}${DOSSIER_CSS}${chrome === undefined ? '' : `${LOCAL_CSS}${DOSSIER_THEME_CSS}${FINDING_CSS}`}`. `chrome` is defined for every operator-agent page (line 613: `const chrome ... = local === undefined ? undefined : {...}`), and `page` draws each of them (lines 633 and 887–891). So every operator-agent page's `<style>` gains `FINDING_CSS` (`.name-index{...}.route-where,.route-see{...}` and the rest, `dossier-finding.ts` lines 178–180), including pages that hold neither a route nor an index entry. That is a byte change the spec does not state, and the 2.6 Falsifier clause quoted above is satisfied by every render, of every draft schema. It also contradicts the carried 2.5 sentence on style rules (line 76): "These style rules SHALL be carried by a page on which a produced figure of either kind renders its two forms, and by no other page ... so a page without such a figure keeps its bytes". 2.5 chose that page-scoped form so that pages keep their bytes, and 2.6 does not follow it.

Smallest repair: in code, carry `FINDING_CSS` only on `find-by-task.html` and `name-index.html`, the pattern 2.5 uses. Alternatively, state the style rules in the fragment-identity paragraph, add them to the line-299 exception and to the preamble, and qualify the Falsifier clause.

### F2 — blocking — "a path a secret detector matches ... is never a name" is not made true by the identifier rule

Location: subject line 90: "a path a secret detector matches has no source page and is never a name". Falsifier (2.6 clause): "the index shows ... a path a secret detector matches". Identifier rule, line 88: an identifier is a backticked span "that is not a path or directory of this index (with or without its final "/") nor, in any case, a term's title".

The exclusion covers only paths *of this index*. A path a secret detector matches has no source page by construction, so it is never a path of this index, and nothing in the identifier rule excludes it. A block that writes such a path in backticks makes it an identifier entry. [Observed] Probe: `buildNameIndex` with one block whose prose is ``Read `conf/token.pem` first.`` and no paths returns `identifier:conf/token.pem`. [Observed] `dossier-finding.ts` takes identifiers from `identifiersIn(block.prose)`, and its exclusion set `taken` holds only `pathNames` (paths that passed the source-page test) and units. [Observed] In `render.ts` the block prose screen is `screen.screenBody(prose)` (line 504), a body detector; the path screen `screenPath` is applied to listed paths and inventory titles (lines 332, 376), and no reading of this review found it applied to prose. [Inferred] Whether such prose already reaches a section page unscreened is a question about versions before 2.6. The index promises more than that: it states an absolute SEC-5-flavoured guarantee its own matching rule does not deliver, and it then aggregates the name on a page built for finding names. The render-test fixture checks this only for a step that *cites* the secret path (`render.test.ts`, "withholds a step whose cited file is withheld ..."). Such a step is withheld whole, so the test does not reach this case. [Unknown] Whether any shipped secret path detector would match a path written only in prose; this review did not run one.

Smallest repair: add to the identifier rule "nor a span a secret detector matches as a path (the screen's path detector), nor one the body detector matches". In code, pass the screen's path predicate into `buildNameIndex` and exclude matching spans. Add a fixture case in which a non-withheld block writes a secret-matching path in backticks.

### F3 — non-blocking — the unit and path kinds are not ordered "without regard to case"

Location: line 88: "the names of one kind ordered without regard to case and then by code unit".

[Observed] `dossier-finding.ts` sorts units with `[...unitNames].sort()` (line 105) and paths with a plain code-unit comparison (line 112). Only terms, identifiers and figures use `byName`. Probe: units `['Zeta','alpha','a','a-b']` come out `Zeta/, a/, a-b/, alpha/`, and paths `Beta.c, alpha.c`. The stated rule gives `a-b/, a/, alpha/, Zeta/` (the units are also sorted before the "/" is appended, which reorders `a` and `a-b`) and `alpha.c, Beta.c`. The unit test "orders entries by kind, then by name without regard to case" uses only lower-case units, so it does not catch this. Repair: sort every kind with `byName` over the displayed name, including the final "/", and add a mixed-case unit and path to that test.

### F4 — non-blocking — a figure entry can show two links with the same words, and a repeating list inside a collapsible section is not listed first

Location: line 90: "a further place of the same words in one entry adds " (2)", " (3)" and so on"; line 88: a figure "is named first by each list that repeats it".

[Observed] `buildNameIndex` puts `figure.repeatedBy` first and then the result of `naming(...)`, which numbers duplicate words only within its own result. Probe: a repeating list labelled "Core" plus a block in section "Core" that writes the title gives two links, both reading `Core`, with no " (2)". [Observed] `dossier-site.ts`, `repeated`: `if (fold === null) repeatedLists.push(...)`, so a list that repeats a diagram inside a draft `details` element is not recorded as repeating it, and the figure entry does not name it first. The spec carries no exception for that case. Repair: number across the whole entry, and either record nested repeating lists (by the outer collapsible's fragment) or state the exception.

### F5 — non-blocking — "distinct file" and "its source page" are undetermined where one file has several source pieces

Location: line 86: "for each distinct file the step cites that has a source page"; line 88: a path's "home is the exact text on its source page".

[Observed] A file can map to several source ids. `render.ts` `pieceAt` assigns pieces, and `dossier-site.ts` builds index paths from `quotable.filter(source => source.path === path)`, `pieces[0]` giving the home. `where` deduplicates by source id (`[...new Set(sourceIds)]`), not by path, so a step citing two pieces of one file shows that file twice under "Read or change: ". The index's home is the first piece's page, by an order the spec does not state. Repair: state that a file split into pieces is linked once, at its first piece in source order, with its lines joined. Alternatively, have the code deduplicate by path.

### F6 — non-blocking — a withheld step still draws its "In this dossier" link

Repair: omit `see` for a withheld step, or state that it is kept.

### F7 — non-blocking — the "only changes" sentences are overbroad for a draft that has routes

Location: preamble line 3 and line 84's last sentence, as quoted under F1.

[Inferred from code] Route steps are blocks of `local.blocks`, and a withheld step is an Unknown block (`render.ts` lines 504–512). The page-wide count `unknownClaims = [...local.blocks.values()].filter(b => b.marking === 'unknown').length` (`dossier-site.ts`), which feeds the one sentence on every page, and the appendix and withheld-item counts therefore change with route steps. So every operator-agent page can change by more than identities and links. These changes follow correctly from "Every rule ... SHALL apply to a route step unchanged", but the two sentences deny them. Repair: say "for a draft without `taskRoutes`, by nothing else; a draft's route steps are counted wherever its claims are counted".

### F8 — non-blocking — the `field-version` detail and the v5 gate hang on a moving constant

Location: line 80: `field-version` "with the detail `` `taskRoutes` needs draft schema polaris-dossier-local-draft-v5 ``", for "a draft in schema v4 or earlier".

[Observed] `check-derive.ts` builds the detail from `LOCAL_DRAFT_SCHEMA_VERSION` and gates on `const v5 = doc['schemaVersion'] === LOCAL_DRAFT_SCHEMA_VERSION`. Both are correct today, since the constant is v5 (`design.md` line 7 says so). [Inferred] Once the adopted 2.4 and 2.5 implementations raise the constant to v7, the detail will read `...-v7`, and a v5 or v6 draft carrying `taskRoutes` will receive `field-version`, contradicting "v5 or later". The gate pattern is older than 2.6 (`home` uses it), but 2.6 adds a literal detail that depends on it. Repair: write the detail as a literal and gate on membership in {v5, v6, v7}. Alternatively, record the dependency in `design.md`.
