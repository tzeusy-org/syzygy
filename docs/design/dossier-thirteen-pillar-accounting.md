## What the brief asks the author to explain

[Inferred] Put the following ordered identities, names and reader questions in one versioned pillar registry. The brief reads the questions, check uses the identities, and the overview uses that same order and names. The future operator-agent brief replaces the old four-topic list with this registry and explains the three allowed dispositions. Keep the rest of the brief, including the pinned-run identity and claim, citation and screening rules.

| ID | Pillar | Reader question |
| --- | --- | --- |
| `purpose` | Purpose, users and non-goals | What problem does the product address, for whom, and what does it leave out? |
| `system-map` | System map | Which moving parts exist, and how do they fit together? |
| `domain-model` | Core concepts and domain model | Which concepts and domain relationships does a reader need to understand? |
| `lifecycles-and-flows` | Lifecycles and request flows | How does work move from entry to completion or failure? |
| `feature-verticals` | Feature verticals | How do the major capabilities work end to end? |
| `data` | Data | What does the product store, transform, migrate and retain? |
| `interfaces` | Interfaces | How do clients, operators and extensions interact with it? |
| `runtime-and-operations` | Runtime and operations | What runs where, and how is it configured, operated and diagnosed? |
| `security-and-trust` | Security and trust | Where are the trust boundaries, and which controls and limitations matter? |
| `performance-and-cost` | Performance and cost | Which resources, limits and cost drivers are supported by evidence? |
| `engineering-quality` | Engineering quality and Tech Standards Critique | Which engineering practices and trade-offs can a reader verify or judge? |
| `history-and-decisions` | History, decisions and open questions | Which past choices explain the current shape, and what remains unresolved? |
| `how-to-change-it` | How to change it | Where should a maintainer start and how can they verify a change? |

## Draft and check

[Inferred] The later supported operator-agent draft carries a bounded `pillars` list with one entry for each registry identity. A list lets check name both copies of a duplicate identity before a decoder could overwrite one. Each entry carries its identity and exactly one of these forms.

- `covered` supplies one or more distinct local section identities. The declared sections exist in the draft and each produces a local reading target. The same section may address different pillars. The registry contributes no facts about the repository.
- `notApplicable` supplies a nonempty reason and at least one structurally valid citation. At least one admitted citation must support the displayed Inferred assessment. A visible, well-supported reason might explain why a command-line-only fixture has no daemon lifecycle.
- `unknown` supplies a nonempty reason. For a supported draft with no evidence for a pillar, the author uses this form and the map renders it as Unknown. The reason may say which evidence is missing in terms permitted by the existing screen.

[Inferred] Reject an unrecognized identity, duplicate pillar, missing pillar, malformed disposition, duplicate section reference within a pillar, unknown section, or section that cannot produce a local reading target. Give each predicate a named repair finding tied to the allowed field path. Use the existing schema bounds and check stages for identities, section references, reason claims and citations. A malformed or missing required citation is a repair finding under the existing citation rules. A structurally valid source reference that the screen withholds follows the existing withholding rules. Project text and citations remain subject to the same review, read and screen gates as other evidence. [VIS-2](../../.syzygy/governance/doctrine/vision.md), [SEC-5](../../.syzygy/governance/doctrine/security.md).

[Inferred] Generate pillar-depth advice in the existing reader-advice module from the permitted coverage and citation results check already derives. Emit one advisory for each visible `covered` pillar with admitted support and fewer than two distinct supported sections or fewer than three distinct admitted source paths cited by those sections at the pinned revision. Multiple citations to one path count once. The advisory can give both deficient counts and supplies no repair finding.

[Inferred] Preserve the bead's author repair loop through the ordinary operator-agent check report. The proposed brief tells the author to consult the pillar-depth advice in the JSON result of `syzygy dossier check <run>` when revising a draft and to repeat check after a revision. This is a proposed separate report field from the same reader-advice module. The existing `readerAdvice` field remains the counted standard set that feeds the versioned durable `readingLedger`. The new advice field feeds the author directly without adding a tally to that ledger or a delta to `readingDifference`. The eventual semantic delta must state that carrier and storage distinction. Receipt of advice sets no outcome, schedules no repair cycle and adds no readiness condition. Evidence depth on a real dossier waits for the admitted source breadth tracked by `syzygy-3efd.1`. The existing source read rules apply throughout. [Reader-advice module](../../packages/polaris-dossier/src/reader-advice.ts), [check and report](../../packages/polaris-dossier/src/check.ts), [check command](../../packages/polaris-dossier/src/cli.ts), [reading ledger](../../packages/polaris-dossier/src/reading-ledger.ts).

## Overview, visibility and compatibility

[Inferred] When the draft layer is permitted, render the map on the overview as a list in registry order. A supported `covered` row links to the admitted sections that render at this revision, using their existing section anchors and protected labels. It reports how the draft assigns coverage; independent fidelity review remains responsible for whether the sections explain the pillar. A visible supported `notApplicable` row carries its screened reason, citations and Inferred mark. An `unknown` row carries its screened reason and Unknown mark. The machine view derives the same visible pillar identities, dispositions, marks and permitted target associations from the same screened result. The map supplies no aggregate completeness score.

[Inferred] Give each not-applicable reason its own claim identity in the existing fidelity packet, tied to that pillar and exact frozen draft. A current validated fidelity verdict for that reason must find that the admitted cited evidence substantiates it before an output presents the reason as Inferred. This uses the existing claim review and packet binding. A current verdict that lacks supporting evidence for the reason, a stale verdict, or no verdict gives any otherwise permitted map row the fixed Unknown reason “Applicability evidence is unresolved” without reproducing the unsupported text or its citations. The existing review and readiness rules still decide whether a render can be served. [REQ-035 fidelity and packet binding](../../openspec/changes/dossier-run-tree-read-bounds/proposed/polaris-generation/spec.md).

[Inferred] Apply the established draft-layer visibility gate before either output. With a wholly withheld draft, both omit the map and all pillar-specific output. With a visible allowed draft and a row whose reason or supporting sources are wholly withheld, emit only the existing scoped Unknown treatment and allowed metadata for that pillar. No authored reason, withheld path, link to withheld content or hidden count beyond existing policy appears. A declared `covered` row whose links lead only to sections without supporting evidence also displays Unknown, with a fixed explanation and no claim of supported coverage. If some linked sections have admissible supporting evidence, link to those alone and use the inherited qualified disclosure. Derive both outputs from the same result. [Existing withheld-citation scenario in REQ-034](../../openspec/changes/dossier-system-model/proposed/polaris-generation/spec.md).

[Inferred] Older supported operator-agent drafts that render and lack the pillar record show the explicit overview text “Pillars not accounted” when their draft layer is visible. They retain their existing section and Pole routes, with no synthetic pillar rows, advice or machine coverage. The normative successor must describe this specific compatibility change where an inherited byte-parity rule otherwise applies. Keep provider draft, brief, HTML and machine bytes at their golden baseline. Poles remain agent-named groupings, so pillar count neither sets nor renders a Pole count. For a newly configured operator-agent run the proposed implicit Pole limit is six, matching the six available renderer hues. Retain explicit run limits and the effective limit for older run forms under their adopted rule. Define exactly how the run and version pin the new implicit limit at adoption. [Dossier renderer](../../apps/three-surface-poc/src/polaris-generation/dossier-site.ts), [provider golden](../../apps/three-surface-poc/src/polaris-generation/dossier-render-provider-golden.test.ts).

[Inferred] The system figure, feature-verticals section and Tech Standards Critique may supply existing admitted section identities for pillars 2, 5 and 11, whichever delivery lands first. The map consumes an actual rendered section association. A sibling's title, proposed target or planned output supplies no link or evidence. Keep the independent chart design within pillar 10 if its later adoption produces a suitable admitted section. [Feature-vertical declarations](dossier-vertical-declarations.md).
