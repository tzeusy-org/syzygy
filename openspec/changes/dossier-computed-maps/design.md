## What the structure record holds today

[Observed] Syzygy derives three things about the tree, and only one of them is an evidence artifact a page may draw as Observed:

| Derivation | Where it lives | What it holds | Status a page may give it |
|---|---|---|---|
| The derived record, `derived/rev-<n>.json` (version 2.3, `derived-record.ts`) | Written once by check beside the check record, published as `derived-structure.json`, re-derived and compared at every render | Rule `top-level-unit` version 1 only: `tree-root` (files at the root), `top-level-unit` (each top-level directory and its file count, at most 250 listed, the rest counted in `unitsNotListed`), `contains` (root to directory); and the record's `files`, `secretPathsLeftOut` and `submodules` | Observed where the currency policy declares `pinned-revision` for `top-level-unit@1` and the record is current; otherwise Unknown |
| The structure record (`derive.ts`, line 1) | On check's report only, "never written into the check record or any gated artifact, never handed to the author in the brief, never rendered" (`derive.ts`, lines 6 and 7) | Top-level units, vendored and generated sets, languages, traits | None: it is not kept as an evidence artifact, and the currency policy declares no bound for its other rules, so any of its facts on a page would be Unknown with `no-currency-bound-declared` |
| The declared manifest facts (version 2.7, `manifest-facts.ts`) | The check record's last member, `manifestFacts`, which lies within the agent sessions' write reach | `package`, `module`, `workspace-member`, `dependency` (with section and group), `workflow`, `workflow-trigger`, `job`, `job-needs`, each with rule, version, path and lines; per-recognizer coverage; caps of 250 files per recognizer and 1,000 facts listed | Inferred only: version 2.7 says no manifest fact is labelled Observed until a later version names a recognizer's mutation record, and "no reader at this version takes a manifest fact from a stored check record; a later consumer re-derives the facts" |

## Which maps are possible now

[Inferred] Each map is specified only from facts that exist, at the status those facts carry (VIS-2):

| Map | Possible now | Status | Source facts | Page |
|---|---|---|---|---|
| Directory map | Yes, at the top level only | Observed where the derived record is current, otherwise Unknown with the region's reason | `top-level-unit@1` facts of the readable derived record, as the region states them | `maps/directories.html`, `Directory map` |
| Unit map | Its units and the packages placed in them: yes. Arrows between packages: deferred | Package and module boxes Inferred; place boxes carry their derived fact's mark (Observed, or Unknown) | `package` and `module` facts of the four package recognizers, re-derived at render; `tree-root` and `top-level-unit` facts for the places | `maps/units.html`, `Unit map` |
| CI pipeline map | Yes, for GitHub Actions workflows | Inferred | `workflow`, `workflow-trigger`, `job` and `job-needs` facts of `github-actions-workflow@1`, re-derived at render | `maps/ci.html`, `CI pipeline map` |

[Inferred] Deferred, with reasons:

- Arrows between packages in the unit map. A `dependency` fact states that one file declares a dependency named X; drawing an arrow from that package to the package of the tree whose manifest declares the name X states that the declaration resolves to it, which version 2.7 says no manifest fact states. Names are written as declared and never normalised (a Python requirement `Foo_Bar` against a project `foo-bar`), a Cargo dependency key can rename its crate, and two manifests may declare one name, so such an arrow can be false. It needs its own rule, version, fixtures and mutation run, as version 2.7 requires of a recognizer, before it is drawn even as Inferred.
- Directories below the top level. No rule derives them and the currency policy declares no bound for any other rule, so they would render Unknown; the directory map says so in its coverage line.
- The structure record's other facts (vendored, generated, languages, traits) on a map: not an evidence artifact and no currency bound (table above).
- Any map element Observed beyond version 2.3's: a manifest fact becomes Observed only by a later version naming its recognizer's mutation record (version 2.7).

So of the three maps the bead names, the directory map is the Observed one; the CI pipeline map is possible only from Inferred workflow facts; and the unit graph is possible only as a placement of Inferred packages in their units, without its dependency edges. The bead's "complete and Observed" holds for the directory map alone, and the spec labels the other two Inferred.

## Re-deriving manifest facts at render

[Inferred] Version 2.7 forbids taking a manifest fact from a stored check record (it lies in the agent-writable run directory), so the render derives its own member by the same rules (`deriveManifestFacts`), from the tree it lists, through its pinned object reader, under the bound screen and content classes it already loads (`render.ts`, lines 169 to 191). This costs up to 1,250 blob reads per render, each bounded at 1,048,576 bytes. Two renders in which no read is refused give the same member (version 2.7's determinism sentence), so the map pages are stable across renders. The scenario "Maps never read the stored check record" pins it with a planted member.

## Figures that fit without shrinking

[Observed] A scratch test calling `layoutDiagram` with `READABLE_SPACING` (the spacing `figureLaidOutWidth` and the derived region use; `diagram-layout.ts`, line 57; `dossier-site.ts`, line 884) gave these laid-out widths: one column 248 px (a root with 1, 2, 12 or 24 children laid out in two columns gave 648); a chain of 3, 4 or 7 boxes 1048 (three columns, wrapping into bands); with `maxColumns` set to 2, chains and fans of 2, 3, 7 and 24 boxes all 648, and one-column graphs with back arrows from 248 to 261. [Observed, at review] With `maxColumns` 2 only a plain chain wraps into bands; a graph of three or more layers that is not a plain chain (a fan, a join or a skip) is stacked (`stackDiagram`, `diagram-layout.ts`, lines 137 to 140), about 248 to 261 px wide for up to 16 boxes, wider with many lanes. So a CI job graph's W is 248 to 261 px, 648 px, or the stacked width, never above 966. The scratch file was deleted; the numbers follow from `NODE_WIDTH` 200, `MARGIN` 24 and the readable `gapX` 200 (two columns: 2 × 200 + 200 + 2 × 24 = 648; three: 1048).

[Inferred] Rule chosen: a map drawing uses the readable spacing at most two columns wide, so W is at most about 648 px for a directory or unit figure, and always at most 966 (the 1440 column) for any map figure, the container query being written per W; it holds at most 25 boxes (twelve units or packages and their place, or 24 jobs), so a large map is several figures; and it has two forms switched by a container size query, as version 2.5's sequence and swimlane figures do, so at 390 px (column 261) it shows its text form at 13 px rather than a drawing scaled below 11 px. The map's own style rules (`map-forms`, `map-list`) are distinct from version 2.5's figure-kind rules, so version 2.5's scenario "Graph figures unchanged by figure kinds" ("its pages carry none of the figure-kind style rules") stays true. A CI workflow of more than 24 jobs is listed rather than drawn: a job graph cannot be paginated without cutting its `needs` arrows.

## Provenance and imitation (RFC7-28)

[Observed] RFC7-28 (`rendering-and-surface.md`, line 101, found through `DIRECTIVE-REGISTER.md`): "Curated diagrams claim no reproducibility-from-snapshot and must not imitate the computed map; embedded computed visuals inherit the map surface's obligations; curated/computed provenance is a machine-readable attribute on every visual." [Inferred] Each map figure carries `data-visual-provenance="computed"`, each drawn element its fact's identity (`data-derived-id` or `data-manifest-id`), each list entry rule, version, path and lines; the map surface's obligations it inherits are stated where they bind: the evaluation on the surface (RFC9-38, the note), Unknown never invisible with its RFC2-24 reason (RFC9-27, each Unknown file's reason), and the unmapped never disappearing (RFC9-44, the coverage line partitions each denominator). No draft member reaches a map page, so a curated figure cannot be placed among computed ones; a draft figure repeating a map's labels keeps `curated` and its own marks (scenario "Draft cannot reach or imitate a computed map").

## Advice classes and the run file (syzygy-3efd.64)

[Observed] The only advice to the author that check carries is on its report: the reader advisories (`reader-advice.ts`, RS-13, RS-14, RS-16, RS-17, RS-19) and the figure-fit entries, which the report carries because it spreads the stored record (`check.ts`, lines 293 to 327). The author repairs from that report (`polaris.ts`, line 473: "run syzygy dossier check ...; repair every finding and check again until it passes"); `figureFit` is read by no other packet (a sweep of `packages/polaris-dossier/src` and `apps/three-surface-poc/src/polaris-generation` outside tests finds it only in `check-model.ts`, `check.ts`, `cli.ts`, `figure-fit.ts` and `reading-ledger.ts`). So "repair packet" here means check's report.

[Inferred] Which advice no author can act on, by the widths above: every reader advisory is fixable in the draft (retitle, cut, draw, cite, merge). A graph figure laid out in two or more columns is at least 648 px wide, wider than the 261 px column at 390, and no change confined to the figure's graph members makes the layout draw it narrower. An author could restate the content as a `sequence` or `swimlane` (drawn at the column's width) or reshape the graph until the layout stacks it, but that advice is about the renderer's forms, not the figure's content; routing these entries to the run is this version's judgment, and a renderer form that stacks any graph (the pursuit's Q6 slice 1) would make them clearable. In the operator-agent mode, graph figures are laid out at 248 to 261, 648 or 1048 px, and at 1440 none of these fails (1048 shrinks to 966, text 11.98 px), so at this version the `mechanism` class is in practice every entry at 390 of a multi-column graph figure, plus the entry Unknown because no layout was supplied (which only a CLI wiring change clears). Remaining entries, such as one at 390 for a one-column graph widened past 261 px by back arrows, or one Unknown because the layout failed on the draft's own fault, stay `author`. The rule is stated by width, not by the figure's count of arrows, and only a graph figure's entry carries numbers (the other v7 kinds take the column's width and never fail), so it is computable from the entry alone.

[Inferred] Where the run record lives. The bead names `run-record.ts`, whose file is `run.json`. It is written at init, re-validated in full on every read with exact keys and a bound of 65,536 bytes, 256 values and depth 4 (`run-record.ts`, lines 104 and 105), and it is the operator-declared, Inferred configuration every step reads. Writing check-derived advice into it on every check would mix Syzygy's computed advice into an operator's declaration, would need a new run-record format, and would put the run's binding record at risk of a failed rewrite on every check. Chosen: a separate run file, `run-advice.json`, whose writer and reader sit beside `run-record.ts` as the bead suggests, computed from the run's check records alone (so it is re-derivable, needs no read-modify-write, and a planted file changes nothing: nothing reads it). The check record and its ledger stay byte for byte as version 2.8 writes them, so the advice is moved, never dropped, and its count is in the file (`occurrences`) and on each report (`mechanismAdvice`).
