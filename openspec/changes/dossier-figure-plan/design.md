## D2. Places, not pages

- [Observed] The bead asks for a plan "for each page". At version 2.23 a draft's page division depends on Poles: without Poles each section is a page; with Poles a Pole page holds several sections, and a Pole holding only the why section has no page (version 1.x Pole paragraph). A deep dive has its page only when produced.
- [Inferred] The plan is keyed instead by the places a figure can be homed (version 2.2): the overview, each section, each deep dive, written exactly as a diagram's `home`. That keeps the plan a function of the draft alone, independent of Poles and dispositions, and makes the match to a figure one comparison: the figure's `home` equals the entry's place. A Pole page then holds the plans of its sections, and the landing page the overview's plan.

## D3. The plan's form

- [Inferred] Two forms, not one with optional members. A planned figure has a question, a kind and a figure; an omission has a reason. A place where no picture answers better than text has no question to write, so forcing `question` and `kind` onto every entry would invite filler.
- [Inferred] Every place must be planned, once. The bead's "for each page" and its acceptance "each planned figure is matched to a figure or a reasoned omission" are both met by requiring an entry per place, each either matched or omitted with a reason. An unplanned diagram is allowed: a place may hold more figures than its one planned answer, and the duplicate rule (D6) catches the common waste.
- [Inferred] The plan's text is plain text, not a claim block, and renders nowhere. This departs from version 2.20's hero omission, whose reason is a claim block because it renders on the landing page. The plan is the author's working record: its question names what a reader would ask, which is no fact about the subject, and nothing of it reaches a reader, so it needs neither label nor citation nor fidelity entry. Rendering it would add text that restates figures (RS-20) and an unreviewed reader-facing surface.
- [Inferred] A planned figure whose diagram is not `produced` raises no finding, as a hero whose diagram is not produced raises none (2.20 D5): the disposition already records why it was not drawn.
- [Inferred] The v12 schema document admits any value at `figurePlan`, so every failure of the plan's form is a `figure-plan` finding with a literal detail, the pattern 2.20 used for `hero` at `$.hero`. One detail covers every malformed entry, so the author reads one instruction for one entry, and an entry that is not well formed is read by no other plan finding, so a malformed entry does not also report a duplicate place or a misplaced figure.

## D4. The plan gates; the advice does not

- [Observed] The bead's exclusion reads "advice in this slice, no gate"; its first acceptance criterion reads "A draft's figure plan validates and each planned figure is matched to a figure or a reasoned omission".
- [Inferred] This version reads the exclusion as governing the three figure advisories, and the acceptance as asking for a validated plan, so plan findings are repair findings like every other form finding, and the advice gates nothing. The plan's findings are all about the plan's own form and its match to the draft; none judges a figure's content, so none can make an author draw a figure that would not be true: an omission with a reason always clears a place.
- [Inferred] The alternative, an optional plan whose failures are advice, was rejected: a plan the author may skip silently is not written "before the prose", and an unchecked match would let a plan name figures that are not there. This reading is the one a reviewer should test first; if the owner or a reviewer reads the exclusion as covering the plan, the change is local: make `figurePlan` optional and move the plan findings into `figureAdvice`.

## D5. Advice as a report member, not a counted reader standard

- [Observed] The bead's design suggests "a new figure-policy module called from `reader-advice.ts`" and notes that "a counted rule needs its text in `reader-standards.ts` first". At 2.23, reader advisories are counted by the reading ledger under exactly the five keys `RS-13`, `RS-14`, `RS-16`, `RS-17` and `RS-19`, and the ledger is written into every draft check record, whatever the schema. `polaris-reader-standards-v1` is carried in the brief and the design packet and shipped as the skill's reference file, and "a version moves only with its bytes" (`reader-standards.ts`).
- [Inferred] Making the three rules counted standards would move the reading ledger's bytes for every draft of every schema and need a reader-standards v2 that moves every brief's bytes. So this version keeps them out of the reader standards and out of the ledger: a member `figureAdvice` on check's report alone, beside the `author`-class advice and without a class member, as the inventory-coverage advice of version 2.12 is. The implementation may still compute it in a figure-policy module called beside `readerAdvice`; what the spec fixes is where it is reported.
- [Inferred] Each rule carries an id and a version, as the mechanism rules of version 2.9 do, so a later change to a predicate is a new rule version stated by a later version of this requirement.

## D6. The three predicates

- [Inferred] Each predicate reads the draft's produced diagrams alone, so it is a pure function of the draft's bytes and decidable by a literal fixture. Each fires at most once per figure, naming the first witness, so a figure's advice is one line.
- Information floor. [Inferred] The bead's measure, "a chain of three or fewer is a sentence", is read as three boxes joined by two arrows. For a graph: at most three nodes and at most `nodes − 1` edges, which takes in a chain, a fan and a disconnected pair; a triangle of three edges, which carries a cycle a sentence states badly, is the near miss. A swimlane's steps are its boxes, chained by the arrows Syzygy draws (version 2.5), so at most three steps; a sequence's messages are its arrows, so at most two messages. The near misses are a fourth node, a third edge among three nodes, a fourth step and a third message. The edge count decides the graph case, whatever its shape: two nodes joined both ways with a third node apart (three nodes, two edges) is advised on although it holds a two-node cycle, and only the three-edge triangle is spared; the line is an exact count, chosen over a shape test a reader could not apply by eye (review 1, note 13). A containment's groups are its boxes and each nesting its arrow, so three groups (one inside the next, or two inside a third) is the same chain or fan; a fourth group is the near miss.
- Duplicate. [Inferred] Two figures duplicate when one draws nothing the other does not: every box and arrow of one is among the other's. Identities cannot be compared (they are unique), so boxes and arrows are compared by their labels, normalised by trimming, collapsing white space and folding ASCII case only, a fold every implementation spells the same way. An arrow is keyed by its ends' labels, not its own label, since two figures drawing one connection may word it differently. Families keep a sequence (an order of events) from duplicating a graph that draws the same pairs. Containment, not only equality, is advised on, because a smaller figure repeating part of a larger one is the common case; of two equal figures only the later is advised on, so the author is told once. A figure needs an arrow or step to be advised on, so two figures sharing one lone box are not. A figure's keys are a set: multiplicity and the order of messages and steps are not compared. So two sequences of the same messages in another order are advised on as duplicates, accepted on purpose: the advice is a prompt to check, the reader still sees the same pairs twice, and keying by position would stop a shorter figure from being found inside a longer one (review 1, note 6). A containment's keys are its groups' labels and, for each nesting, the pair of parent and child labels (`in`); containments form a family of their own, since boxes within boxes state only containment, which a graph states with an arrow of another meaning.
- Mixed levels. [Inferred] "Level" is decided only where the draft says what a box stands for: the `unit` a v9 node may carry. Enclosure is defined for the two units whose extent is a region of the tree: the repository root encloses every unit with a place in the tree (all but `dependency-name`), and a top-level directory encloses a package manifest, workflow job or compose service whose path lies under it. A graph that draws the enclosing and the enclosed unit with no chain of `contains` edges leading from the first to the second mixes levels; with such a chain, direct or through intermediate units (root, directory, manifest), it shows the containment on purpose, which is what a containment or boundary figure does. A chain is accepted, not only a direct edge, because version 2.23's witness table can witness only a top-level directory inside the root, so asking for a direct root-to-manifest arrow would push authors to an arrow that renders Unknown (review 1, finding 2). The near misses are the `contains` arrow, two top-level directories, and a directory name that is only a prefix of a path (the directory `pack` beside a fixture manifest whose path begins packages/). A containment carries units on its groups (version 2.23), and its nesting is its statement that one holds the other, so a containment says X holds Y exactly where Y is drawn inside X at any depth. A containment is the form that answers this advice: drawing the root and one of its directories as two side-by-side top-level groups is advised on; nesting the directory in the root is not.
- [Inferred] Limits, stated so no reader takes silence for a pass: a node without `unit` is never compared, so the mixed-levels rule says nothing about most drafts until authors name units; labels that differ in more than case and white space are not duplicates; nesting among package manifests is not compared at this version.
