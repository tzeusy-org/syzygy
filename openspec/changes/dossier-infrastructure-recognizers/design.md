## The five recognizers, and why each reads what it reads

[Inferred] Each reads the fields the bead names (services, images, ports, depends_on; kinds and names; resources and modules; targets; projects and targets) and nothing else, and states a declaration, never its effect. Each choice below keeps a recognizer a pure function of one admitted body and its path, so the version 2.7 driver (`manifest-facts.ts`, `deriveManifestFacts`) takes them unchanged in shape: one more entry each in `MANIFEST_RECOGNIZERS` (line 85).

- `compose-file`. The path rule is the Compose specification's default file names and their override names; any other `*.yml` is not claimed (it falls in the remainder). The reader is version 2.7's YAML reader (`manifest-yaml.ts`), which refuses an anchor, an alias and a merge key (its header, lines 8 and 9). Many Compose files use `x-` anchors and `<<: *defaults`; at this version they are Unknown `beyond-reader`, which is honest and visible, and a reader change to resolve merge keys is a later rule version. Ports: the short form is a string or an integer; the long form is a mapping, of which `target` and `published` are read and written in the short form's order. An integer needs its text, which the reader does not keep today (`MNode` `other`, `manifest-model.ts` line 17): the requirement asks the reader to keep it. `depends_on` in both forms; a long form's `condition` is not read. Values are taken as written: Compose interpolates `${VAR}` from the environment at run time, so resolving it would be a claim about an environment Syzygy does not see.
- `kubernetes-manifest`. Kubernetes manifests have no fixed file name, so the path rule names YAML files under directories whose names conventionally hold them, and leaves out `templates` (Helm templates are Go templates over YAML, which the YAML reader would refuse as `syntax`, filling the Unknown list with files that are not manifests). Reading every YAML file in the tree was rejected: it would spend the read limit on configuration that is not Kubernetes, and a document lacking `apiVersion` or `kind` is already counted as no object, so the narrower rule loses only files under unconventional directories, which the remainder counts by directory. The reader must read several documents for this recognizer alone (today a second document is `beyond`, `manifest-yaml.ts` line 459); the workflow and Compose recognizers keep refusing it, so `github-actions-workflow` keeps its version. Facts carry `kind` and `metadata.name` only: `namespace` and `apiVersion` were weighed and left out, because the bead asks for kinds and names, and because a third body-taken string in the widest fact would push the member's bound (below) by about 1.5 MB.
- `terraform-configuration`. Only `.tf` files, only top-level `resource` and `module` blocks. `.tf.json` is JSON syntax with a different structure and is left to a later rule; `data`, `provider`, `variable`, `output` and `locals` blocks are skipped as the bead asks. A module's `source` must be a literal string (Terraform itself requires one), so a template sequence in it is `field-type`. The workspace has no HCL parser; the requirement states the minimum a small lexer must read (comments, nested blocks, bracketed expressions across lines, templates with nested strings, heredocs), so a body that only looks like a block inside a heredoc yields nothing (scenario "Terraform resources and modules, ...").
- `makefile`. GNU make's default names; under 2.0.0 only `Makefile` is admitted. Make has no grammar in the sense TOML or YAML do: the reader classifies each logical line, and the faults follow GNU make's own errors (a recipe before the first target, a missing separator, an unterminated `define` or conditional are errors make reports). A line beginning with a function call (`$(eval ...)`) can declare rules no reader sees without expanding make's language, so it is `beyond-reader`: the file is Unknown rather than read partially, as the bead's "a refusal is Unknown, never partial facts" rule (version 2.7 design) requires. Targets holding `%` or `$`, and special targets and suffix rules (a word beginning with `.` and holding no `/`), are not literal targets of the file and yield no fact. One fact per distinct target, at its first rule, because make merges the rules of one target. Prerequisites are not read: the bead names targets only, and a prerequisite is often a file, not a target, so stating it as an edge would be a claim the text does not make.
- `cmake-lists`. The CMake language is small and fully specified, so the reader reads all of it and has no `beyond-reader` fault. `project` and `add_executable`, `add_library`, `add_custom_target` give projects and targets with their kind; `target_link_libraries` and `add_subdirectory` were weighed and left out (the bead names projects and targets; links belong with the relation types of syzygy-3efd.28). Arguments keep `${...}` and `$<...>` as written.

[Inferred] Set apart: the five new recognizers set apart vendored, generated and test paths by the same rules as the package recognizers (`derive.ts`, `setApartPath`, line 105), so a Compose file in a `test/` fixture or a Makefile under `build/` is not the project's. Disjointness: the Compose rule and the workflow rule exclude each other's paths, and the Kubernetes rule excludes both, so one path is a candidate of at most one recognizer and the remainder's identity holds.
