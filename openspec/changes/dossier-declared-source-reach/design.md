## Decisions

**D1 — A new file, two stages.** [Observed] The predecessor policy is bound by digest to adoption A-4 (`scripts/check_spec_reconciliation.py`, `DECLARED_SOURCE_SUBJECTS`) and named as base by the URL origin/species policy (`basePolicy.reviewedSha256`), so it is not edited. The successor keeps the predecessor's five content-classification rules (their `rule` texts, lists and pinned prose byte-identical in value) as Stage 1 and adds three rules with ids that only read what Stage 1 leaves unplaced. This makes "no predecessor outcome changes except by a new denial" a property of the structure rather than of a review of three dozen list entries, and it keeps every digest the implementation already pins for Stage 1 valid.

**D2 — Class of each admitted kind (RFC5-14).** Design, architecture, ADR, RFC, specification and manifesto documents are `governance-text`: RFC5-14 defines the class as "Doctrine, spec, decision, policy text" and excludes from project-documentation a document "the project's declared classification policy places as doctrine, spec, decision or policy text"; design and architecture documents govern how the project is built. Nested READMEs, guides and other prose are `project-documentation`. Configuration (YAML, TOML, JSON, HCL, proto, CMake, Make, Dockerfiles) is `code-content`, as the predecessor already reads configuration written in a source extension ("Configuration written in a listed extension (for example a .config.js file, setup.py or a .sh file) is therefore code-content"); RFC5-14's vocabulary is closed and no other class fits.

**D3 — Every Stage-2 body is screened at least as strictly as any predecessor body.** No Stage-2 body is named by either active-content exemption or by span redaction: the exemption's `appliesTo` and the redaction's `appliesTo` get new texts naming Stage-1 bodies only, so an MDX page with JSX or a nested README with an HTML badge is excluded as active content, and any detector match excludes a Stage-2 body whole under either visibility. Six `configurationDetectors` run over Stage-2 bodies, their cited spans and agent text; they run over no Stage-1 body, so they change no predecessor outcome. This costs reach (D7) and buys a boundary a reviewer can check without trusting new exemptions.

**D4 — The token lists.** The predecessor's 25 `docExcludedTokens` are partitioned exactly (the build script asserts it): `governanceTextTokens` (adr, adrs, rfc, rfcs, spec, specs, specification, specifications, design, designs, architecture, architectures, manifesto, manifestos) are the option's six named families; `withheldTokens` (decision, decisions, governance, policy, policies, security, conduct, doctrine, doctrines, principle, principles) stay indeterminate. The draft reviewed put decision and decisions in the first list, reading decision as the D in ADR; the review (F7) noted that a `decisions/` directory or `decision-log.md` is not an ADR, so they moved to the second list and Q-2 asks the owner. A path with a word from both lists stays indeterminate. Admitting the second list is an owner question (Q-1). [Inferred] Word matching misplaces some paths by rule, lawfully (RFC5-14: the declared policy decides each file) but not by their true class: an RSpec `spec/` tree's Markdown fixtures, packages/design-tokens/README.md and a `spec-helper/` README become governance-text.

**D5 — Notebooks left out.** A notebook text cell is a JSON string inside the `.ipynb` blob. REQ-polaris-generation-034 verifies every quotation against the pinned blob's bytes, so a cited cell needs an extractor and a quotation rule over the decoded cell, and the outputs (which can carry data and printed secrets) must stay unread. That is a separate design; a `.ipynb` path stays indeterminate. [Inferred] handson-ml3 is the repository this costs most.

**D6 — Vendored paths.** Stage 2 places nothing below a directory named in `vendoredDirectoryNames` (node_modules, bower_components, jspm_packages, vendor, vendored, third_party, third-party, thirdparty, external, externals, extern): RFC5-14's project-documentation is "a project's own prose", and vendored configuration is not the project's. Stage 1 is unchanged, so a predecessor-admitted source file under `vendor/` stays admitted.
