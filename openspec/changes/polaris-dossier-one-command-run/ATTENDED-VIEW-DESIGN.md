## Same-run attachment and recovery

[Inferred] Use a single stable run heading with the run identifier and current attempt, then the actual step, original deadline, limit status and what the operator can do. Show an observed state only when the trusted supervisor has current evidence for that run and attempt. The view is a projection of those records. The existence of a terminal pane, old receipt or stored snapshot cannot establish that work is continuing. If the view or attachment evidence is absent, stale or disagrees with the run or attempt, show Unknown with its reason and offer safe help. Labels describe their evidence at the stated observation time.

[Inferred] A verified detach opens one interval on the same run and live attempt with its observed start time. Show the attach action and original deadline. The already-admitted attempt may progress under its existing authorities and deadline while detached. Verified reattachment to that same attempt closes the interval once with its observed endpoint and restores the run view. The attempt, pin, deadline and permissions stay bound. Repeated or stale attach events cannot open or close another interval, launch a child or repeat a stop. Unknown endpoints remain explicitly Unknown. A terminal cue cannot make any authority grant or replace validation of the current supervisor record.

| Verified condition | First cue | Action or recovery |
|---|---|---|
| Live and detached | `Detached` with the run, attempt and observed start | Show `syzygy polaris --attach <run>`. Observe the existing attempt. |
| Live and reattached | `Reattached` with the same attempt, observed interval and original deadline | Show the current wait and the existing stop action. Attaching again starts no work. |
| Current attachment or progress unverified | `Unknown` with the unavailable, stale or differently bound evidence | Show bounded help for rechecking the same run. Give no assurance of continued progress or cleanup. |
| Stop requested, cleanup unverified | `Stopping` and the outstanding cleanup check | Acknowledge repeated stop as the same request. Defer resume while cleanup is unverified. |
| Stopped, cleanup verified, resume still eligible | `Stopped` with its observed time and verified cleanup | Show `syzygy polaris --resume <run>` with the original pin, deadline and current validation gates. |
| Resume refused | Safe reason and resulting run state | State what condition an operator can correct. Keep the previous attempt stopped. |

[Inferred] A verified stopped run may use the existing resume action and its gates. That action can start a replacement attempt after the required checks. Reattaching to a live attempt affects only the view. Preserve the original deadline through either action. Exceeded bounds and refused or unverified outcomes keep their existing terminal or Unknown states. No step advances because the view was connected or opened twice.

## Questions, ordinary waits and readable cues

[Inferred] A wait line identifies the actual step and whether action belongs to the operator. An authorized author question has the textual cue `Waiting for operator` and the name of the Author pane. A system wait names the pending operation and can say `No action needed`. An unavailable observation says `Wait state: Unknown` with the applicable reason. A displayed author question offers the existing authorized route only after its own checks. Reading a role window or focusing it does not deliver input. Inventory, fidelity and design windows expose admitted progress metadata only. This proposal adds no way for either the operator or Syzygy to send arbitrary role input, no authority to display source or transcript bytes, and no change to the author-only disclosure, role receipt or permission rules.

[Inferred] Keep state, reason and the next permissible action readable as ordinary text without color or mouse. Name the keyboard focus action from the run view through the existing multiplexer keyboard affordance, keep help discoverable from that view and preserve a text cue when no multiplexer view is available. Acknowledge the known stage before a wait. Pace and actual accessibility are measured on the authorized implemented surface. Keep the stated epistemic level and reason in narrow output as well as the ordinary terminal view.
