# Design: run-tree read bounds for REQ-033, REQ-035 and REQ-048

Version 2.18, for bead syzygy-3efd.80. It extends the reader rule of REQ-polaris-generation-034 version 2.10 (one non-blocking open of the path, regular files only, a bound checked from the descriptor's size and at most one byte read past it) to every remaining unbounded read of a run-tree file, in the requirement that states the file. Code is cited at `origin/main` `c900e87119e872db9eb2db5d06ca60512ffc3a0b` (PR #908, which holds the 2.14 code for REQ-034's four files and `readBoundedFile` in `packages/polaris-dossier/src/check-record-read.ts`).

[Inferred] The words chosen: wherever a reader's existing outcome names an error code, the bounded reader's two refusals would otherwise print `unknown-error` (`NotARegularFileError` carries no `code`) or `byte-limit` (`BoundedJsonError`'s code); the text names `not a regular file` and `larger than <bound> bytes` instead, so a reader sees why, as version 2.14 chose for the frozen draft revisions. Every other outcome is the reader's existing outcome for a file it cannot read, so no word changes there.

[Inferred] Polarity. A file that stands at its path but cannot be read is not evidence of absence (VIS-2: no evidence is Unknown, never zero). So close records an unreadable step or breach log as Unknown with its cause, and only an absent log as empty (review finding 1, repaired; the first draft had specified an unreadable log as an empty one, which is a zero standing in for missing evidence). Two readers still take an unreadable file as a value that is not fail-closed on its own, and both are bounded by another rule: the supervisor takes a run record it cannot read as no repair-cycle limit, but the reverification refuses every step on such a run, so no step runs past the limit; and status takes a close record it cannot read as usage `not recorded; the Execution Record cannot be read`, which is the Unknown form, never zero. A supervisor started for a named run over a state path it cannot read now refuses rather than starting the run afresh and writing over (or blocking on) whatever stands there (review finding 4).

[Inferred] A validated review check record (outcome `validated`, `problems` empty) holds only fixed words, digests, safe integers, the verdict's file name and a session identifier of at most 200 characters (`declaredSessionId`), so it lies far within 262,144 bytes; a refused record may be larger, and the supervisor reading it as no checked verdict changes nothing, since it treats a refused record as `none` today (`verdictFor`, `polaris.ts` 757–760).

## Bytes this version changes

[Inferred] None for a regular file within its bound: every reader reads exactly the bytes it read before, and no step writes or renders a different byte. Only the outcomes and words in the table above change, for a path holding something that is not a regular file, a file past its bound, or a file that grows past it while read; and the close record (`record.json`) changes in its `steps` and `credential.breaches` members, only for a step or breach log that stands at its path and cannot be read. The provider golden (`apps/three-surface-poc/src/polaris-generation/dossier-render-provider-golden.test.ts`) is unaffected.

## Residuals

- [Observed] `launch-disclosure.ts` 89 (`launch.json`) has no product caller and is not specified (the table above).
- [Inferred] A file read under its own size (the inventory brief, and a packet whose readable delivery record states no size) is bounded only by what the file holds when opened: a regular file the agent made very large is still read whole, and the digest Syzygy recorded refuses it after the read. For the inventory brief no writer cap exists to derive a stated bound from because Syzygy records only its digest (`session-handover.ts` 215), not its length; recording its length beside the digest, as `packetBytes` is for a packet, would let a later version state a writer-derived bound (review finding 5).
- [Inferred] The packet's bound is read from the run directory's delivery record, which lies within the agent sessions' write reach, so an agent can raise or remove its `packetBytes` and have a large regular packet read whole (review finding 2). The digest comparison still refuses any packet that is not the one Syzygy wrote; the bound only stops a reader blocking on, or reading without limit from, something that is not a regular file.
- [Observed] Two stat-then-read paths outside the run tree, on files the agent sessions can write, are not covered by this version (review finding 3): `clone-head.ts` 21–34 (`readSmall`: an `lstat`, then a whole `readFileSync` of the clone's `HEAD` and refs) and `launch-clone.ts` 83 (an `lstat`, then an open with `O_NOFOLLOW` but without `O_NONBLOCK`, so a FIFO swapped in between blocks the open). They need a follow-up bead under the requirement that states the clone's refs; this package files none (the spec worker runs no tracker mutation) and names them in its report.
- [Inferred] The 16,777,216-byte bounds of the two logs, the close record and the supervisor's state are readers' bounds, not writer guarantees: a long run could in principle write more. No run has been measured near them.
- [Observed] Operator instruments under `scripts/` (`dossier_run_evidence.mjs`, `dossier_scale_measure.mjs`, `dossier_rerender_measure.mjs`, `dossier_coverage_precheck_replay.mjs` and the like) read run-tree files but lie outside the swept population on purpose: an operator runs them by hand over a run they chose, no requirement states them, and no step's outcome rests on them (review finding 9).
- [Observed] `scripts/count_polaris_effective_scenarios.py --selftest` fails on `origin/main` at `c900e871` with `raw-read disclosure: URL source v2.1 and source policy v3 must be effective` before this package (run on an export of that commit); this package does not change that.
